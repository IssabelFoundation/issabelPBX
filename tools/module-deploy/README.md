# Deploy selected IssabelPBX modules from Git

`tools/deploy-modules` deploys committed changes to installed modules without the
Module Admin screen. It uses the **installed** Issabel libraries for dependency
checks, upgrades, configuration generation and Asterisk reload. It never runs
`install_amp`, downloads modules, updates framework, or restarts Asterisk.

## Requirements

- Run as root on a Linux PBX with PHP CLI **7.4+**, POSIX, SimpleXML and SQLite3
  with online-backup support. The target modules must support that PHP version.
- Git, GNU `cp`/`tar`/`stat`, `runuser`, and `mysqldump` for MySQL/MariaDB installations.
  GNU tar must support ACLs, extended attributes and SELinux metadata. With
  SELinux enabled, `restorecon` must also be available.
- A working Issabel database and Manager connection, an installed non-root
  Asterisk account, and readable SQLite AstDB (`astdb.sqlite3`). Main databases
  supported in v1: MySQL/MariaDB and SQLite3. Legacy Berkeley AstDB is not supported.
- Database backup privileges, including locking tables and dumping routines,
  events and triggers. MySQL dumps use table locks to include legacy MyISAM
  tables consistently; these locks briefly block database writers.
- Enough space for module/configuration snapshots, staging, database and AstDB
  backups. Planning checks estimates with a reserve; applying must successfully
  complete the backups before modifying module files.

Keep this tool and its `module-deploy` directory together, outside the web root.
The helper must be readable through its parent directories by the configured
Asterisk user. A clone under `/usr/src` generally fits; a private `/root` clone
may not. CLI syntax checks use the PBX's PHP CLI, not a separate development PHP.

Run in a controlled maintenance window. Do not edit configuration, run Module
Admin, or apply changes concurrently. The tool serializes its own deployments
with `/var/lock/issabelpbx-deploy.lock`; Issabel's GUI does not share that lock.
An initial pending-reload check, another pre-write check and file comparisons
detect common conflicts, but they cannot freeze all other PBX configuration
writers. Normal calls are not deliberately stopped by the tool.

## First deployment

Use a trusted, reviewed commit. The tool pins Git objects, disables replacement
objects and hooks for its reads, and does not use the clone's uncommitted files.
It does **not** authenticate the author or safety of a chosen commit.

```sh
sudo /usr/src/issabelPBX-git/tools/deploy-modules plan \
  --repo /usr/src/issabelPBX-git \
  --from INSTALLED_BASE_COMMIT \
  --to REVIEWED_TARGET_COMMIT \
  --modules core,sipsettings
```

`--repo` must identify the repository root containing `core`, `sipsettings`, etc.,
not the workspace parent. Both refs are resolved to immutable commit IDs. The
base commit's module versions must match the installed database versions. Every
affected installed file must match its base Git content and executable bit;
additions must not already exist. A mismatch stops the plan rather than
overwriting local changes. Unaffected files are retained.

If the installed commit is unknown, identify the matching release/commit and
reconcile affected local differences first. Do not guess a baseline or bypass
conflicts. Matching `module.xml` versions alone does not establish matching code.

Planning prints JSON with the root-only plan path, changes, migration list and
explicit Git diff commands. Review those commands' output and the target's
installation scripts before applying. It creates only private deployment state
and temporary lint files, not module/configuration/database updates.

```sh
sudo /usr/src/issabelPBX-git/tools/deploy-modules apply \
  --plan /var/lib/issabelpbx-deploy/plans/PLAN_ID.json
```

Apply requires an unmodified, locally signed plan generated by the same tool
version. It checks the installation, dependencies and file metadata again, backs
up everything, stages all changes and rechecks each destination before writing.
Files are replaced individually with atomic renames. The whole multi-module
deployment is **not** atomic; the maintenance window prevents web requests from
depending on a partially written batch.

Files keep existing owner/group, ordinary permissions, ACLs and extended
attributes where supported. Executable bits follow Git. New files/directories
use the configured Asterisk account; new files get policy SELinux labels. Existing
module-root symlinks are resolved and pinned. Changed paths cannot traverse
symlink parents. Absolute, escaping or parent-traversing Git symlinks and
submodules are refused. Directory/file transitions that conflict with existing
directories are also refused rather than deleting directory contents.

Paths containing `custom` are protected. There is no blanket directory sync or
`rsync --delete`; only the reviewed tracked file deletions are applied. The
generated configuration path is updated through Issabel's native regeneration,
including its existing symlink handling.

## Patches, upgrades and subsequent deployments

Same-version changes are file patches: the tool does **not** rerun installers.
If a version increases, it invokes `module_install(module, false)` in dependency
order. Dependencies inside the selected batch use target versions; other
dependencies and reverse dependencies must remain satisfied. There is no forced
installation, automatic dependency download, new-module installation, downgrade,
or framework upgrade. Selected modules must already be installed and enabled.

Changes to `install.php`, `install.sql`, `uninstall.php`, declared install
includes, migration/upgrade/install directories or SQL files require a module
version increase. This is a conservative direct-file check, not a full analysis
of every installer include or side effect; review upgrade scripts as code.

One final native configuration generation/reload covers the batch. The helper
checks the regeneration result **and the AMI Reload response**, because this
framework's `do_reload()` alone does not validate that response. It then checks
Manager/database connectivity, installed module versions and deployed contents.
No extra Asterisk restart is performed. Pre/post-reload hooks configured in
Issabel still execute and can have their own effects.

After a successful deployment, the next plan can omit `--from`; the baseline is
recorded per module. Applying the same recorded target is a no-op:

```sh
sudo /usr/src/issabelPBX-git/tools/deploy-modules plan \
  --repo /usr/src/issabelPBX-git --to NEXT_COMMIT --modules core,sipsettings
sudo /usr/src/issabelPBX-git/tools/deploy-modules history
```

Options `--state-dir DIR` and `--bootstrap FILE` are available on every command.
Use one permanent state directory per PBX; the default is
`/var/lib/issabelpbx-deploy`. It must be private, root-owned and outside the web
root. Keep its signing key and history with the PBX, not in Git. Do not edit
signed plans. A source/runtime/tool change requires a newly reviewed plan.

## Backups and recovery

Each deployment keeps a private directory under `deployments/ID` containing:

- A journal (`record.json`) with the signed plan, per-file fingerprints, stages,
  completed writes, results and errors.
- Database SQL or an online SQLite backup, and a checked online SQLite AstDB
  backup. These are consistent **per database**, not a single atomic snapshot
  across the PBX's different stores.
- Full selected-module and Asterisk-configuration tar archives, including ACLs,
  extended attributes, SELinux metadata and links; archive/database checksums.
- Original affected files/configuration entries and staged committed bytes.
- Protected native-operation JSON logs. Installer output can contain secrets;
  it is not printed in the public command result. Keep backups private.

For a completed **patch without migrations**:

```sh
sudo /usr/src/issabelPBX-git/tools/deploy-modules rollback --deployment DEPLOYMENT_ID
```

Rollback verifies backups, destination fingerprints and configuration state
before restoring. It refuses a newer deployment, later operator edits, or
changed permissions. It removes added files, restores changed/deleted files and
previous generated configuration, and reloads once. Empty directories created
by deployment may remain; unrelated files are not removed.

A patch failure during writes/reload attempts automatic recovery of completed
writes, configuration and a reload. It never restores the database automatically
and never overwrites changed `custom` configuration during recovery. A failed
recovery is recorded as `recovery-required`.

**Once an upgrade installer has started**, automatic file-only rollback is
refused, even if the installer reports an error. The current code and database
may already depend on each other. Keep the maintenance window in place and use
the retained backups for an explicit recovery:

1. Inspect `record.json`, native logs, the migration scripts and backup checksums.
   Decide whether to repair forward or restore; account for data written since
   the snapshot before restoring the database.
2. For a full restore, stop relevant writers in a planned outage. Restoring AstDB
   requires taking Asterisk's active SQLite connections out of use. Restore the
   selected module archives, original configuration, main database and AstDB as
   one reviewed recovery operation, including removing reviewed added files.
   Restoring tar archives alone does not remove new files.
3. Regenerate, reload/start as appropriate and validate database versions,
   endpoints, registrations, web UI and representative calls. Reconcile any
   later local data/configuration changes explicitly.
4. Only after recovery succeeds, restore `current.json` to the journal's
   `plan.previous` map if the old deployment was restored, and mark that journal
   `status` as `manually-recovered`. Preserve the original journal/backup first.
   For a forward repair, record/reconcile the actually installed commits instead.

Interrupted/incomplete deployments also block subsequent plans/applies until
reconciled. There is intentionally no command that blindly acknowledges a
failed migration or restores a live database. Inspect recovery before unblocking.
Backups are not automatically pruned.

## Tests and first PJSIP rollout

```sh
php tools/module-deploy/tests/run.php
php core/tests/pjsip-trunks.php
```

The deployment suite creates disposable Git repositories and a simulated PBX.
It covers committed-vs-dirty content, patch/upgrade ordering, additions/deletions
and links, local conflicts, late edits, altered plans, dependencies, installer
version checks, backup/reload/migration failures, recovery, repeat deployment,
backup integrity and exclusive locking. It also exercises the real helper's
structured error/shutdown contract. It does not run a real migration, MySQL
dump, GNU metadata restore or Asterisk reload.

For the current PJSIP fix, commit the complete reviewed changes to `core` and
`sipsettings` first. Plan their **joint** deployment from the productive base
commit, including the new shared helper and `core/etc/pjsip.conf`; uncommitted
working-tree fixes cannot be deployed by this tool. Run the procedure first on
a PBX clone with the target PHP, Asterisk and database versions.

Acceptance on that clone must cover a real dump/restore, ownership/ACL/SELinux,
native upgrade scripts, an apply failure, generated includes, PJSIP's loaded
identifier order, the web UI, registrations and calls on both a traditional
trunk and Wuzapi. If the web PHP runtime disables OPcache timestamp validation,
use its established cache-invalidation procedure; a CLI reload does not clear a
separate web runtime's OPcache. This tool does not restart the web server.
